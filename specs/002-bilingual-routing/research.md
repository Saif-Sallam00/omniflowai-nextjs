# Phase 0 Research: Bilingual Routing Foundation

**Spec**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

Two open research items were scoped by the operator for this slice. Both are resolved below with no new runtime dependency and no new environment variable — both outcomes were verified against the constitution's Scope Discipline principle rather than assumed.

---

## Research Item 1: i18n mechanism — library vs. hand-rolled

**Decision**: Hand-rolled. No i18n library (e.g. `next-intl`, `next-i18next`) is introduced. No new dependency is added to `package.json`. **Unchanged and still approved** — only the *sub-decision* of how `<html lang dir>` is set (below) has been reopened and reversed; the library-vs-hand-rolled call and the mirrored literal route trees stand as originally decided.

**Rationale** (unchanged):
- The spec's own architecture (constitution Principle VII, "Bilingual By Architecture") stores translated *content* per-row in Postgres (`articles`, `project_translations` — confirmed present and empty in the Phase 0 schema), not in static message-catalog files. The problem an i18n library like `next-intl` is built to solve — managing large sets of static UI-string translations, ICU pluralization/formatting — doesn't exist here: this slice has zero visible UI strings requiring translation (thin placeholders only, per spec Assumptions), and future slices' real translated content comes from the database, not from a translation dictionary. A library license for that problem would be paying for a capability the project doesn't need.
- Next.js 16's App Router has no built-in i18n routing primitive (this was reconfirmed against the spec's own framing — "no locked architectural decision covers this choice"). What *is* needed — resolving a language from a URL, setting `<html lang dir>`, computing a counterpart URL, and building per-page metadata — is a small amount of pure logic and one root-layout change. None of it requires a routing framework.
- The asymmetric URL scheme this project requires (English unprefixed at root, Arabic under `/ar/*`, **no** `/en/*` — standing rule 002) doesn't match the shape most i18n libraries assume (typically a uniform `/[locale]/*` prefix for every locale, default locale included). Adopting one would mean fighting its default routing conventions to reproduce a shape hand-rolled code produces naturally.
- Constitution's Scope Discipline principle requires explicit justification for any new dependency. No such justification exists here — the requirement is fully satisfiable without one, so none is added.

- **Routing** (unchanged): mirrored file trees under `app/` — English pages at their existing unprefixed paths, Arabic pages under `app/ar/*`. Plain Next.js file-based routing — no dynamic `[lang]` segment, no rewrite. This satisfies FR-008 (404 on unknown routes) automatically: an unmatched path in either tree has no `page.tsx` to match, so Next.js's default not-found behavior applies with zero extra code.
- **Per-page metadata (FR-005/FR-006) and URL-pairing (FR-007)** (unchanged): plain TypeScript helper functions in `lib/`, consumed by each page's `generateMetadata` — see [data-model.md](./data-model.md).

### `<html lang dir>` (FR-004) — REOPENED and REVERSED

**Original decision (superseded below)**: keep the single existing root layout (`app/layout.tsx`, shared by every route including `/admin/*`); extend `proxy.ts` to compute the language from the request path and forward it via a request header; have `app/layout.tsx` read that header via `headers()` to set `lang`/`dir`.

**Why reopened**: that decision was made by weighing only *how much Phase 0 code gets restructured* — it did not evaluate what calling `headers()` (a Dynamic API) inside the app's single root layout costs in rendering mode. That cost turns out to be severe and was missing from the original comparison, so the decision is reopened here rather than left standing on an incomplete evaluation (constitution Principle I, Diagnosis Before Solution).

**The cost, made explicit**: `app/layout.tsx` is the outermost layout for the *entire application* — every route, public and `/admin/*` alike, renders underneath it. A Dynamic API call (`headers()`, `cookies()`, `searchParams`, or an uncached `fetch`) anywhere in a layout opts that layout **and everything nested below it** into request-time dynamic rendering, because the whole tree is produced by one render pass rooted there. Calling `headers()` in `app/layout.tsx` therefore forces **every route in the application — every current and future Phase 1 public page, and `/admin/*`** — into full dynamic SSR on every request, with no static generation and no ISR possible anywhere in the app, for as long as that call stays in the root layout. The original decision treated this as a one-line, low-risk change; it is actually an app-wide, standing rendering-mode commitment.

**Required research check — is Partial Prerendering (PPR) stable in the pinned Next.js 16.3.1, and does it change this tradeoff?** Verified directly against Next.js's own documentation (fetched 2026-08-25, matching the pinned `16.3.1`; see Sources):
- PPR's configuration surface is genuinely stable in Next.js 16: the old `experimental.ppr` flag and the route-level `experimental_ppr` segment export were **removed**, replaced by a top-level, non-experimental `cacheComponents` config option. So enabling `cacheComponents` would **not** violate the constitution's "canary/beta/RC prohibited" rule on its own terms — that rule targets the Next.js *release channel*, and this is a stable-channel, stable-namespace config key.
- However, it is **opt-in and default-off** ("It is not enabled by default"; Next.js 16.3 release notes confirm `cacheComponents` "and `partialPrefetching` flags are still opt-in even on stable"), and adopting it is explicitly **not a rename-only change**: Next.js's own upgrade guide states it "requires adopting the Cache Components model" and "can surface build errors for uncached data outside of `<Suspense>`." That is a standing architectural adoption with no locked decision covering it — exactly the kind of unjustified scope expansion Scope Discipline prohibits if pulled in solely to patch this slice's root-layout problem.
- More decisively: **PPR would not actually fix the `headers()`-in-root-layout problem even if adopted.** PPR's mechanism is Suspense-boundary-based — it lets a page keep a static shell while carving out *inner* dynamic islands that stream in after the initial response. But `<html>` itself, rendered by the root layout, is the outermost wrapper of the entire tree — it sits **above** any point where a Suspense boundary could be placed. A per-request value needed for `<html>`'s own attributes can't be deferred into a streamed-in island without violating FR-004's explicit requirement that the correct `lang`/`dir` appear in the *initial* HTML response — deferring it would mean the first bytes sent carry a default (wrong) value until the dynamic island resolves and patches it in.
- **Conclusion: PPR does not change the tradeoff.** It neither rescues the header-forwarding approach (the specific problem sits structurally above what PPR can help with) nor supplies a justification to adopt it here (it's an unrelated, non-trivial architectural commitment this slice doesn't need). This finding stands independent of the scope/restructuring cost argument below — it is a separate, sufficient reason on its own to abandon the `headers()` approach.

**New decision**: two independent root layouts via top-level route groups — `app/(en)/layout.tsx` (`<html lang="en" dir="ltr">`, hardcoded literal JSX) and `app/ar/layout.tsx` (`<html lang="ar" dir="rtl">`, hardcoded literal JSX) — **not** `app/(ar)/...` (correcting the operator's proposal: `(ar)` in parentheses would be URL-transparent like `(en)` and resolve to unprefixed `/`, colliding with English; `ar` must be a real path segment, exactly as it already is in the current mirrored-tree design, for the `/ar` prefix to exist at all). `app/admin/*` moves to `app/(en)/admin/*` — a pure filesystem move: route groups add no URL segment, so `/admin/*` URLs are unchanged, and since every file under `app/admin/**` already imports via the `@/*` absolute alias (verified — `app/admin/**` has zero relative (`../`) imports across `actions.ts`, `layout.tsx`, `page.tsx`, `login-form.tsx`, `sign-out-button.tsx`), the move requires **zero content edits**, only a directory move. `proxy.ts` is **untouched** — no broadened matcher, no header-forwarding responsibility; its existing `/admin/:path*` matcher and cookie-redirect logic are unaffected because route groups don't change the URLs it matches against. No page anywhere in either language tree needs a Dynamic API to determine `lang`/`dir` — each tree's root layout hardcodes its own fixed value — so every route (public and `/admin/*`) remains eligible for Next.js's normal default static rendering (or ISR, or `cacheComponents`/PPR adoption later for unrelated per-page dynamic-data reasons) exactly as it would if bilingual routing didn't exist at all.

**One behavioral note, not a cost**: navigating between a page in the `(en)` root layout and one in the `ar` root layout is a full page reload rather than a soft client-side transition, because they're different root layouts (documented Next.js behavior for multiple root layouts). For a language switch specifically — where `lang`/`dir` and the entire page must change together — this is the correct, expected behavior rather than a regression; it's also irrelevant to this slice, since the language-switcher control that would trigger such a navigation is out of scope until slice 1B.

**Alternatives considered**:
| Option | Rendering-mode cost | Rejected because |
|---|---|---|
| Single shared root layout + `proxy.ts` header-forwarding + `headers()` in `app/layout.tsx` (original decision) | **Severe**: forces the entire application — every public page and `/admin/*` — into full dynamic SSR on every request, permanently, with static generation and ISR unavailable anywhere. Not fixed by adopting PPR/`cacheComponents` (see research check above — the dynamism sits above any possible Suspense boundary). | Was chosen by weighing only file-restructuring cost, without evaluating this rendering-mode cost. Reopened once that cost was made explicit. |
| `next-intl` | N/A (not selected for other reasons, unchanged from original research) | Solves static message-catalog translation, which this project doesn't need (content is DB-driven); its default `/[locale]/*` routing convention doesn't match the required asymmetric root/`/ar` scheme without extra configuration to fight it; adds a runtime dependency with no corresponding justification. |
| Single `app/[lang]/...` dynamic-segment tree with a middleware rewrite of `/` → internal `/en` | Neutral-to-good (segment gives static `params.lang`, no Dynamic API needed) | Still works, but needs a rewrite layer translating every English URL to a hidden `/en` segment purely so the segment can exist, plus the same root-layout/`/admin/*` question the route-groups option answers more directly — more moving parts for the same outcome. |
| **Multiple root layouts via top-level route groups (`app/(en)/...` incl. moved-in `/admin/*`, `app/ar/...`) — SELECTED** | **None** — every route keeps Next.js's normal default static-rendering eligibility, since `lang`/`dir` is hardcoded per tree rather than resolved from a per-request Dynamic API. | Previously rejected solely for moving `/admin/*` into a route group. That move is now confirmed to be a zero-content-edit, pure directory move (every admin file already uses the `@/*` absolute alias), which is a smaller and more precisely-scoped cost than forfeiting static rendering for the whole application. Now selected. |

## Research Item 2: absolute-URL base for canonical/hreflang

**Decision**: Reuse `BETTER_AUTH_URL`. No new environment variable is introduced.

**Rationale**:
- `.env.example` already documents `BETTER_AUTH_URL` as "Base URL of this deployment (e.g. `https://<app>.replit.app`), used by Better Auth" — it is already the deployment's canonical origin, not narrowly an auth-only value. This deployment has exactly one public origin (Replit Autoscale, per Phase 0's `.replit`); there is no second domain for canonical/hreflang URLs to legitimately differ against today.
- `lib/env.ts` already validates `BETTER_AUTH_URL` as a required, boot-time-checked URL. Reusing it for absolute-URL construction adds zero new required secret, zero `.env.example` change, zero `lib/env.ts` schema change, and zero new Replit Secret to configure per environment.
- Introducing a second variable (e.g. `SITE_URL`) that would hold the identical value in every current environment is the duplicate-configuration anti-pattern the constitution's Scope Discipline principle (and the operator's standing "no speculative configurability" guidance) warns against: two variables holding one fact invites drift when only one is updated.

**Alternatives considered**:
| Option | Rejected because |
|---|---|
| New dedicated `SITE_URL` (or similar) env var | No current or near-term scenario exists where the public site origin and `BETTER_AUTH_URL` diverge; adding it now is speculative configurability for a problem that doesn't exist yet, contradicting Scope Discipline. |

**Forward-looking note (not a present ambiguity, recorded for later)**: if a future phase puts the public site behind a different origin than the one Better Auth uses (e.g. a CDN or custom domain in front of the app, with auth staying on the Replit origin), `BETTER_AUTH_URL` will need to be reconsidered as the canonical/hreflang base at that time. Nothing in this slice or the current deployment topology makes that split real today, so it isn't solved here — noted so it isn't silently forgotten.

**How it's used** (implementation detail for `/speckit-tasks`): a single small accessor (e.g. `lib/site.ts`) re-exports `env.BETTER_AUTH_URL` under a name that reads correctly at every call site (`siteUrl`, or similar) — a naming/readability concern only, not a new source of truth.
