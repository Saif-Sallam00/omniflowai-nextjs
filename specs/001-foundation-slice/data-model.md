# Data Model: Foundation Slice — Phase 0

**Source**: `spec.md` § FR-3 (Target schema), FR-4 (Authentication). All entities below are defined by the spec, not invented here — this document formalizes them as a data model reference for implementation.

**Scope note**: All application entities (Article, Project, ProjectTranslation, Lead) are schema-only in Phase 0 — tables exist, are indexed and constrained, but hold zero rows at Phase 0 completion (FR-3.8, AC-5). Only the Better Auth entities are populated, and only by the bootstrap script and acceptance-verification login/logout activity.

## Entity: Article

Represents one language-specific version of an article. Multiple `Article` rows sharing a `translation_group_id` are translations of the same conceptual article.

| Field | Type | Constraints |
|---|---|---|
| `id` | serial | PK |
| `translation_group_id` | uuid | NOT NULL, default `gen_random_uuid()` |
| `language` | `language_enum` | NOT NULL |
| `slug` | text | NOT NULL |
| `title` | text | NOT NULL |
| `excerpt` | text | NOT NULL |
| `body` | text | NOT NULL |
| `cover_image` | text | NOT NULL |
| `published` | boolean | NOT NULL, default `false` |
| `published_at` | timestamptz | nullable |
| `related_project_id` | integer | FK → `projects(id)`, `ON DELETE SET NULL`, nullable |
| `related_solution` | text | nullable |
| `created_at` | timestamptz | NOT NULL, default `now()` |
| `updated_at` | timestamptz | NOT NULL, default `now()` |

**Unique constraints**: `(language, slug)`, `(translation_group_id, language)`
**Indexes**: `(language, published, published_at DESC)`, `(translation_group_id)`
**Validation rules**: none enforced at Phase 0 beyond schema-level (no write paths exist yet — Phase 2 adds admin CRUD).
**Phase 0 state**: zero rows.

## Better Auth entities — expected reference shape, pending CLI-generated confirmation

**The CLI output is authoritative, not this document.** The exact column-level shape of these five tables is generated by running `npx @better-auth/cli generate` against the pinned Better Auth 1.6.30 with this project's exact config (modelName prefixes per FR-4.15, `username` plugin enabled, database-backed rate-limit storage per FR-4.10). That command produces a Drizzle schema file which is committed to the repo as-is, and the migration is generated from the committed CLI output — not hand-authored to match the table below.

Do not hand-add or hand-edit columns based on the descriptions below. In particular, `auth_session` almost certainly requires a `token` column (used to look up a session by its session token) that is intentionally *not* listed here — it is expected to appear in the CLI-generated schema, and must come from the CLI, not be added manually.

The table below documents purpose and `modelName` mapping only, per spec FR-4.15 — not a column inventory:

| Table | `modelName` | Purpose |
|---|---|---|
| `auth_user` | `user` | Account identity — created by bootstrap, holds the admin's `username`/`displayUsername`. The `email` field is required by Better Auth; populated with a placeholder value (`<username>@omniflowai.local`, `.local` TLD is reserved and non-routable) per FR-4.16, because username-based login is the only authentication method in Phase 0. |
| `auth_session` | `session` | Active login sessions. One row per active login; removed/invalidated on sign-out (AC-9). Expected to include (among other CLI-generated columns) a `token` column — confirm against actual CLI output, do not assume this list is exhaustive. |
| `auth_account` | `account` | Credential storage. For this project's password-based admin, one row per user with `providerId = "credential"`. |
| `auth_verification` | `verification` | Better Auth's verification-token bookkeeping. Unused functionally in Phase 0 (no email verification flow triggered — `emailVerified` is set directly by the bootstrap script) but must exist per schema requirement. |
| `auth_rate_limit` | `rateLimit` | Rate-limit bookkeeping. Schema/table exist per FR-4.10; not actively enforcing in production per FR-4.11/AC-17. |

**Phase 0 state**: `auth_user`/`auth_account` — exactly one row each (the bootstrapped admin) after AC-6. `auth_session` — rows created/removed by login/logout activity during acceptance verification (AC-8/AC-9). `auth_verification`/`auth_rate_limit` — empty (tables exist, unused in Phase 0).

## Relationships summary

```
Project (1) ──< ProjectTranslation (many)   [project_id, ON DELETE CASCADE]
Project (1) ──< Article (many, optional)     [related_project_id, ON DELETE SET NULL]
auth_user (1) ──< auth_session (many)        [Better Auth internal]
auth_user (1) ──< auth_account (many)        [Better Auth internal; one row for password credential]
```

No relationships exist between the application entities (`Article`/`Project`/`ProjectTranslation`/`Lead`) and the Better Auth entities — they share only the same Postgres database/`public` schema and connection pool (FR-3.7, FR-2.7).
