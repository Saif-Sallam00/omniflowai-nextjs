# Phase 0 Research: Admin Dashboard Restyle

All items below were flagged in the source spec's "Notes for `/plan`" as mechanism details deliberately deferred from specification. Each is resolved here with a decision, rationale, and alternatives considered, grounded in the actual current code (`app/(en)/admin/(protected)/**`, `app/(en)/admin/auth/**`) read during planning.

## 1. Presentational component set + prop shapes

**Decision**: Seven components under `components/admin/`, each a plain function component, no client directive unless noted:

- **`AdminShell`** (`admin-shell.tsx`) — Server Component. Renders the sidebar nav region + a `<main>` content region. Props: `{ children: React.ReactNode }`. Composes `AdminSidebarNav` internally.
- **`AdminSidebarNav`** (`admin-sidebar-nav.tsx`) — direct restyle of the existing `admin-nav.tsx`'s nav portion. Stays `"use client"` (it already is, for `usePathname`). Props: none (nav links are an internal constant, exactly as today); accepts the sign-out form as a child or renders it inline exactly as today, calling the unchanged `signOutAction`. Only its returned JSX/className changes from a horizontal top bar to a vertical sidebar list; the active-link detection (`pathname === link.path`) is unchanged logic.
- **`PageHeader`** (`page-header.tsx`) — Server Component. Props: `{ title: string; description?: string; action?: React.ReactNode }`.
- **`Card`** (`card.tsx`) — Server Component. Props: `{ children: React.ReactNode; className?: string }`. A padded, bordered, rounded container — used for the dashboard, form sections, and list-row cards.
- **`Button`** (`button.tsx`) — Server Component (renders a plain `<button>` or, via `asChild`-free convention, just a styled `<button>`; existing submit buttons that need `useFormStatus` — e.g. `SubmitButton` in `article-form.tsx`, `SignOutButton` — keep their own component and simply apply `Button`'s className via a shared `buttonClassName(variant)` helper export, OR render `<Button>` as a thin style wrapper accepting all native `<button>` props via `...rest` so `disabled`/`type` pass through unchanged). Props: `{ variant?: "primary" | "secondary" | "destructive"; } & React.ButtonHTMLAttributes<HTMLButtonElement>`.
- **`FormField`** (`form-field.tsx`) — Server Component. Props: `{ label: string; htmlFor: string; error?: string; children: React.ReactNode }`. Wraps an existing `<input>`/`<textarea>`/`<select>` (passed as `children`, unchanged) with a styled label and an error slot that renders the existing `state.fieldErrors.*[0]` string unchanged.
- **`Table`** family (`table.tsx`) — Server Component. Exports `Table`, `TableHead`, `TableRow`, `TableCell` as thin styled wrappers around `<table>`/`<thead>`/`<tr>`/`<td>`, each `{ children: React.ReactNode; className?: string }`.
- **`StatusBadge`** (`status-badge.tsx`) — Server Component. Props: `{ tone: "neutral" | "success" | "warning" | "danger"; children: React.ReactNode }`. Used for lead status, published/draft, featured/showcase — the page mapping the domain value (`lead.status`, `published`, `featured`) to a `tone` stays in the page/list component, not in `StatusBadge` itself (keeps the component pure/domain-agnostic per FR-002).

**Rationale**: This set covers every visual need identified in FR-1.1 and the four user stories (shell/nav, headers, containers, buttons, form fields, tables, badges) with the smallest possible surface — matching the source spec's own example list almost 1:1. Keeping `Button`/`FormField`/`Table`/`StatusBadge` as plain prop/children wrappers (FR-002, FR-003) means every consumer stays a Server Component except the one file that already legitimately needs `"use client"` (`AdminSidebarNav`, for `usePathname` and, if added, mobile-toggle state).

**Alternatives considered**:
- A single monolithic `AdminUI` namespace/object export — rejected as it would still be one file importable from anywhere, but bundling many concerns together makes future changes to one component risk larger diffs; separate files keep FR-5.3's diff-reviewability property (each file's change is legible independently).
- Making `Button` `"use client"` to support `asChild`/polymorphism (like a shadcn-style API) — rejected: no such library, no such need; existing buttons that need pending state already have their own thin wrapper (`SubmitButton`, `SignOutButton`) that can just borrow `Button`'s className/variant styling as a plain string export instead of wrapping the whole component. This avoids forcing every consuming page toward a client boundary and avoids reproducing library-like polymorphic-component complexity that was explicitly rejected (no shadcn/Radix).

## 2. Palette tokens

**Decision**: A small shared constants module, `components/admin/palette.ts` (or inlined directly as literal Tailwind utility classes in each component — see below), defining the mapping from semantic role to Tailwind gray-scale + one accent utility classes: e.g. `surface` (`bg-white`), `surfaceMuted` (`bg-gray-50`), `border` (`border-gray-200`), `textPrimary` (`text-gray-900`), `textMuted` (`text-gray-500`), `accent` (`bg-indigo-600` / `text-indigo-600` — exact accent hue chosen during implementation from the existing Tailwind default palette, no custom color added to `tailwind.config.ts`), plus the four `StatusBadge` tones mapped to existing Tailwind color utilities (e.g. `neutral`→gray, `success`→green, `warning`→amber, `danger`→red — all default Tailwind palette, no new config).

**Rationale**: Tailwind's default theme already ships a full gray scale and every accent hue needed; adding a constants file of *class-name strings* (not a JS/CSS custom-property theme) keeps this hand-rolled-Tailwind-only, changes zero build configuration, and gives every component a single place to reference so the "neutral + one accent" rule is enforced by convention rather than scattered magic strings. `tailwind.config.ts` itself does not need to change — no new dependency, no new build step, no CSS Custom Property theming layer introduced.

**Alternatives considered**: A CSS-variables-based design-token file (`:root { --admin-accent: ... }`) — rejected as unnecessary ceremony for a light-mode-only, admin-only, small component set; plain Tailwind utility-class constants are simpler and match "hand-rolled Tailwind, no library" more literally.

## 3. Sidebar responsive/mobile approach

**Decision**: `AdminSidebarNav` stays `"use client"` (already is, for `usePathname`) and gains local `useState` for an `isOpen` mobile-toggle boolean, defaulting to a `md:` breakpoint that shows the sidebar permanently on desktop (`hidden md:flex md:flex-col` pattern) and a hamburger-toggle-controlled overlay/drawer on narrow viewports. No new import beyond `react`'s `useState`, `next/link`, and `next/navigation`'s `usePathname` — all already imported today. No server-only module is imported by this file today, and none is added.

**Rationale**: `AdminSidebarNav` (the restyled `admin-nav.tsx`) is already the one and only client component in this part of the tree, already holds the active-route logic, and already renders the sign-out form. Adding toggle state here is the smallest possible change — it does not create a new client/server boundary anywhere else, and every other new component (`AdminShell`, `PageHeader`, `Card`, etc.) stays a plain Server Component, directly satisfying FR-003 and FR-017 (server-only guard keeps passing because nothing new here imports `lib/env`, `lib/db`, or `lib/auth-server`).

**Alternatives considered**: A separate new `"use client"` `MobileSidebarToggle` component holding its own state and communicating via a shared context or URL search param — rejected as an unnecessary extra client boundary and extra file for no behavioral gain; co-locating the toggle state in the nav component that already needs to be client is simpler (KISS, constitution IV).

## 4. Wrapping existing client-component forms without touching their state/logic

**Decision**: `article-form.tsx` and `project-form.tsx` (and their sub-components: `body-editor.tsx`, `cover-image-field.tsx` ×2, `logo-image-field.tsx`, `media-image-field.tsx`, `system-cards-editor.tsx`, `results-editor.tsx`, `chip-input.tsx`) are edited **in place**: every `useActionState`/`useFormStatus`/`useState` call, every prop, every action reference, and every conditional-render branch stays exactly where it is in the function body. Only the JSX returned by each component is restructured to use the new presentational wrappers (`Card` for section grouping, `FormField` around each existing `<input>`/`<textarea>`/`<select>` + its existing `state.fieldErrors.X[0]` text, `Button` variants for submit/add-row/remove-row/upload triggers, `Table`/`StatusBadge` where a list is rendered inside a form e.g. none currently). No new hook, no new prop is introduced into these components; `FormField`/`Card`/`Button` are consumed as plain layout wrappers around the pre-existing elements and their pre-existing `onChange`/`defaultValue`/`name` attributes, which are copied verbatim onto the same underlying `<input>`/`<select>`/`<textarea>` elements.

**Rationale**: This directly satisfies FR-3.4/FR-3.6 ("byte-for-byte" state/actions) and FR-002/FR-003 (presentational components carry no logic) simultaneously — the restyle is purely a JSX-shape change (which elements are nested inside which wrapper) plus a className change, never a props/state/hooks change. Because `FormField`/`Card`/`Button` accept `children`, the existing form elements pass straight through unmodified as children — no adapter layer, no prop-renaming, no behavior surface added.

**Alternatives considered**: Introducing a `useAdminForm` shared hook to unify `useActionState` boilerplate across the two forms — rejected: it would touch the forms' actual state-management code, violating the "byte-for-byte" constraint and the "if restyling seems to need a logic change, STOP and flag it" rule; there is no styling need that requires this, so it is explicitly not done.

## 5. Task sequencing — project form as its own, last, independently-verified step

**Decision**: The restyle is sequenced in this order (to be broken into concrete tasks by `/speckit-tasks`): (1) new `components/admin/*` presentational components, built and, where feasible, sanity-checked in isolation; (2) the `(protected)` layout + `AdminSidebarNav` shell; (3) the three list pages (dashboard, leads, articles) — lower-risk, mostly read-only rendering; (4) the article form and its sub-components — medium risk, verified independently (full article create/edit/publish/delete + EN↔AR pairing + image upload walkthrough) before moving on; (5) the auth sign-in page; (6) the project form and its sub-components, as the **final, isolated step**, with its own independent full walkthrough (create with all three images + system cards + results + both languages, edit, delete) before the feature as a whole is considered done. Steps 1-3 and 5 can complete and be spot-checked locally; steps 4 and 6 each require their own full deployed-URL verification pass per FR-6.2, with step 6's pass being the most thorough given it is explicitly called out as the highest-risk file.

**Rationale**: `project-form.tsx` is the single largest, most stateful admin file (276 lines: transactional save, fan-out assembly, two repeatable-row builders, a chip input, three separate image-upload fields, bilingual sections) — restyling it carries the highest chance of an accidental JSX-nesting mistake that silently drops a `name` attribute or a conditional branch. Doing it last, after the same wrapper components have already been proven correct on the lower-risk article form, and verifying it in complete isolation, directly satisfies the source spec's explicit requirement that this file be "restyled but its logic and the JSX around its logic treated with extra care and verified independently."

**Alternatives considered**: Restyle both forms in a single combined pass — rejected per the source spec's explicit sequencing requirement and constitution IV (scope discipline: isolate the highest-risk change for independent verification rather than bundling risk).

## 6. Deployed-URL verification + seed-data create/verify/delete lifecycle

**Decision**: After each risk-bearing step (article form, project form) and once more at the end for the full slice, verification runs against the deployed Replit URL (not local) with the browser DevTools console open throughout, following this lifecycle to avoid leaving residue in the database:
1. Sign in on the deployed URL.
2. Walk the read-only flows first (dashboard, leads list, articles list, projects list) — confirm no console errors, confirm sidebar/table/badge rendering.
3. **Create** one throwaway article (with a cover image and one inline body image, marked clearly as test data, e.g. title prefixed `zz-restyle-test`) and one throwaway project (with all three images, one system card, one result, both EN/AR content) through the restyled forms.
4. **Verify**: confirm each created item appears correctly in its restyled list, open its edit form and confirm all fields round-trip, publish the article and confirm it renders on its public URL, confirm the project's public URL renders, confirm the still-draft state of anything not published still 404s publicly, exercise the EN↔AR "add version" affordance on the test article.
5. Exercise lead status-change and delete on a real or test lead entry using the restyled controls.
6. Exercise sign-out and re-sign-in.
7. **Delete**: delete the test article (both language rows via the counterpart pairing) and the test project through the restyled delete controls, confirming the delete Server Actions behave exactly as before and the items disappear from both admin and public surfaces.
8. Confirm the browser console shows zero errors across the entire walkthrough (the specific regression class to watch for is the prior env-leak class of error).

This lifecycle is documented as the runnable checklist in `quickstart.md`.

**Rationale**: This mirrors the "live-smoke-test flow already established" referenced in the source spec's own notes, satisfies AC-4 (every flow verified on deploy, console open) and FR-6.2, and satisfies the constitution's "no batch accepted solely on implementer self-report" — an operator runs and confirms this checklist against the running deployed instance. The explicit create→verify→delete ordering guarantees the production/shared database is left clean (no seed residue), matching the source spec's own requirement.

**Alternatives considered**: Verifying only against a local `next build && next start` — rejected: explicitly called out in both the source spec and this feature's FR-019/SC-002/SC-003 as insufficient, since prior bugs (the env-leak class) only surfaced on the real deployed Replit environment, not locally.
