# Implementation Plan: Admin Articles CRUD — Phase 2, Slice 2b

**Branch**: `006-admin-articles-crud` | **Date**: 2026-09-01 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/006-admin-articles-crud/spec.md`, built directly from the pre-approved `docs/articles-crud-slice-spec.md`, grounded in `docs/articles-crud-extract.md`.

## Summary

Add admin create/edit/delete for `articles` — the first slice to write to a table Phase 1 only ever read from. A grouped admin list (`/admin/articles`, one row per `translation_group_id`, EN and AR side by side, ordered by most-recently-updated group) plus two full-page forms (`/admin/articles/new`, `/admin/articles/[id]/edit`) let the admin author bilingual articles: title, language-aware slug (Latin-only for EN, Arabic-script-permitting for AR), excerpt, Markdown body with an inline "insert image" control, a cover image, publish state, and optional related-project/related-solution links. Both image fields upload immediately to Slice 2a's existing `POST /api/image` and store only the returned `/api/image/{id}` path. Three Server Actions (`createArticleAction`, `updateArticleAction`, `deleteArticleAction`), each independently calling `requireAuth()`, drive the mutations through five new/extended `lib/db/articles.ts` functions; `published_at` first-publish-only stamping and the explicit `updated_at` bump both live as DAL-layer invariants, not in the actions or forms. **No schema change, no migration** — the `articles` table is frozen and already matches Phase 0 FR-3.1 verbatim (re-confirmed in the grounding extraction). All six mechanism items the approved mini-spec deliberately left open (AR slug character class + slugify, the grouped-list query shape, the counterpart-create param contract, the `updated_at` bump mechanism, the `useActionState` return shape, and the upload-control client/server split) are resolved in `research.md`, each grounded in an already-shipped precedent in this exact codebase (the admin login form, the public contact form, the leads admin slice, or the old application's own proven article-admin behavior).

## Technical Context

**Language/Version**: TypeScript (strict mode) on Next.js 16.3.1 App Router — unchanged from every prior slice.

**Primary Dependencies**: No new dependency. Reused as-is: `drizzle-orm` (extending `lib/db/articles.ts`, reading `lib/db/schema.ts`'s existing `articles`/`projects`/`project_translations` tables), `better-auth` (`requireAuth()`, already proven), `zod` (already used for `contactFormSchema`/`leadStatusSchema` — reused here for the article form's validation schema), React 19's `useActionState`/`useFormStatus` (already proven by the admin login form and the public contact form), and Slice 2a's `POST /api/image` Route Handler (consumed unchanged, called directly from new Client Components).

**Storage**: Neon Postgres via the existing pooled Drizzle connection (`lib/db/index.ts`, unchanged). **Zero schema change** — no new table, column, index, or constraint; no migration is generated by this slice. The `articles` table (`lib/db/schema.ts:56-91`) is used exactly as Phase 0 defined it.

**Testing**: No automated test framework introduced, consistent with every prior slice's own deferral (1A/1B/004/005). Verification is the quality gate (`tsc --noEmit`, ESLint, `next build`, all zero-error) plus a manual walkthrough of `quickstart.md`, mapped 1:1 to spec.md's eight user stories and ten success criteria.

**Target Platform**: Replit Autoscale — unchanged.

**Project Type**: web-service — unchanged; same single Next.js App Router project.

**Performance Goals**: Not independently load-bearing. The grouped-list query (research.md, Item 2) is a single flat `SELECT` over a low-row-count table, grouped in application code — no pagination or streaming concern at this scale.

**Constraints**:
- **No schema change, no migration** (FR-14.3) — every new capability is DAL + Server Actions + admin UI on top of the existing, frozen `articles` table.
- **Grouped admin list** (FR-1.2/FR-1.4) — one row per `translation_group_id`, ordered by the group's most-recently-updated article descending (a draft has no `published_at` to order by).
- **EN/AR independence** (FR-3.4, FR-4.2, FR-5.1) — no cross-language cascade on edit, delete, or publish; the two rows of a group share only their `translation_group_id` value, never a foreign key.
- **Language-aware slugs** (FR-7.1/FR-7.2) — EN keeps the old app's Latin-only rule verbatim; AR gets its own character class and slugify function (research.md, Item 1) — the old Latin-only slugify is not reused for AR (it would strip Arabic entirely).
- **First-publish-only `published_at` stamping, as a DAL invariant** (FR-5.2/FR-5.3) — ported directly from the old app's own `stampPublishedAt` logic (extraction §5.2), living in `createArticle`/`updateArticle`, not the actions or the form.
- **Explicit `updated_at` bump in the DAL, not `.$onUpdate` on the schema** (research.md, Item 4) — keeps `schema.ts` at zero drift from FR-3.1's literal text.
- **Cover + inline body images go through Slice 2a, unchanged** (FR-8.2/FR-9.2) — the returned `/api/image/{id}` path is stored verbatim; never a data URI, never the bare id. Both upload controls are Client Components calling `fetch("/api/image", ...)` directly — no new Server Action or Route Handler wraps them (research.md, Item 6).
- **Full-page editor, not a modal** (FR-2.1/FR-4.1) — this admin area has no dialog/overlay component system; create and edit are their own routes.
- **`useActionState` error surfacing, modeled on the richer `lib/actions/leads.ts` precedent** (FR-11.1, research.md Item 5) — `{ status, fieldErrors, formError }`, not the simpler two-field login-form shape; actions never silently no-op on invalid input.
- **Every mutating Server Action calls `requireAuth()` itself** (FR-11.2) — independent of the `(protected)` layout's own gate, matching `leads/actions.ts`'s existing precedent exactly.
- **Revalidation spans both admin and public surfaces** (FR-13.1) — `/admin/articles` plus the affected language's public list and detail paths, since those are ISR-cached Server Components reading the same table.
- **`relatedProjectId`/`relatedSolution` stay optional and unconstrained by any new DB object** (FR-10.1/FR-10.2) — `relatedProjectId` sourced from a new `listProjectsForSelect()` in the existing `lib/db/portfolio.ts`; `relatedSolution` remains the fixed four-id application-level convention, no DB enum.
- **Naming/style conventions carried forward** (spec Assumptions, constitution): kebab-case files, default-export page/layout modules, verb-first named exports, `type` aliases (not `interface`), the project's internal path alias only, TypeScript strict throughout.

**Scale/Scope**: One extended DAL module (`lib/db/articles.ts`, 5 new functions), one new export on an existing DAL module (`lib/db/portfolio.ts`, `listProjectsForSelect`), one new small language-aware slug module (`lib/article-slug.ts`), three new pages (`/admin/articles`, `/admin/articles/new`, `/admin/articles/[id]/edit`), a shared `ArticleForm` component plus two small Client Components (cover-image control, body-editor-with-insert-image), three Server Actions, one nav-link addition. No new dependency, no new table, no new Route Handler.

**Structure Decision**: Everything new slots into the `app/(en)/admin/(protected)/articles/` segment (mirroring `leads/`'s existing shape: a `page.tsx` list, an `actions.ts`, small Client Components alongside) plus two nested routes (`new/`, `[id]/edit/`) for the full-page create/edit forms — no modal, no shared dialog component, per FR-2.1/FR-4.1. `article-form.tsx` is shared between create and edit (same fields, same validation, differing only in whether `language` is fixed and whether a `translationGroupId`/`id` is present) rather than two near-duplicate forms, since the two modes differ only in a handful of props, not in structure. The two upload-related Client Components (`cover-image-field.tsx`, `body-editor.tsx`) are split out from `article-form.tsx` itself because they are the only parts of the form that need client-side upload state (loading/preview) — keeping them separate makes clear, at the file-tree level, exactly which two pieces of this otherwise-plain form talk to `/api/image`. `lib/article-slug.ts` is a new top-level `lib/` module (not folded into `lib/db/articles.ts`) because slug validation/generation is pure string logic with no DB dependency, reusable by both the client-side auto-generate-on-type behavior and the server-side validation — colocating it with the DAL would blur that it has no database concern at all.
